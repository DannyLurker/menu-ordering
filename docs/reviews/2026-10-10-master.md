## Summary

The change builds the spec 0002 data model: nine Prisma tables with the required enums, the partial unique index for one ACTIVE stay per room, scrypt PIN helpers, a seed, a proof script, and 14 tests. The unique-index guards are real and tested, and I re-ran the suite myself (8 unit + 6 integration, all green). The headline issue is that the spec promises store-level rules ("store level rules guard bill rows from day one", build plan says the migration satisfies AC-1–AC-7), but the migration enforces only uniqueness — I proved a stay with checkOut before checkIn inserts cleanly, and price/qty/ETA bounds are equally unenforced. Everything else is minor.

## Major
### 🟠 Spec invariants unenforced at store level, `prisma/schema.prisma:43` / `prisma/migrations/20261010085523_data_model/migration.sql:17`
**Problem**: The spec's key invariants — checkOut after checkIn, price nonnegative whole rupiah, qty 1–20, etaMinutes 5–120, failedPinAttempts ≥ 0 — have no CHECK constraints or Prisma-level guards. Only uniqueness is enforced in SQL. I verified empirically: a stay with checkIn 2026-10-20 / checkOut 2026-10-10 inserted without error (cleaned up after). Bounds currently live only as asserts in the throwaway proof script, which is not shipped code, so Slice 1 gets zero DB protection.
**Why it matters**: Negative prices or inverted dates corrupt folio totals (AC-9) and stay validity (AC-1) silently; the spec explicitly claims these are guarded from day one.
**Suggested fix**: Add CHECK constraints to the migration SQL for Stay dates, MenuItem price, OrderItem qty, Order etaMinutes, and nonnegativity on amounts/attempts — or, if deliberately deferred, narrow the spec's "store level rules" claim and record Slice 1 as owning the constraints.

## Minor
### 🟡 Non-constant-time PIN comparison plus no format check, `lib/pin.ts:5`
**Problem**: `verifyPin` compares hex digests with `===` instead of `crypto.timingSafeEqual`, leaking a timing side channel; `hashPin` accepts any string with no 6-digit format enforcement although AC-2 requires 6 digits.
**Why it matters**: Low exploitability at this scale, but this is the security-critical primitive every later slice builds on, and the file header already defers "production policy" to the auth slice without a tracked handoff.
**Suggested fix**: Compare with `timingSafeEqual` on buffers, and either validate 6-digit format here or record the auth slice as owning it.

### 🟡 Seed logs the demo PIN in plain text, `prisma/seed.ts:65`
**Problem**: `console.log` prints "(PIN 123456)" while the spec's key invariants say PIN is "never stored or logged in plain text" and the security model says PIN/session values are never logged.
**Why it matters**: A demo credential, but it normalizes the exact pattern the invariant forbids; logs get copied into tickets and CI output.
**Suggested fix**: Drop the PIN from the log line (e.g. "demo stay room 101 seeded — see local notes for PIN") or mark it explicitly demo-only.

### 🟡 Proof script mixes UTC and local dates, `scripts/prove-data-model.ts:15`
**Problem**: `todayLocal()` uses local getters but `stayCoversToday` formats stored dates with `toISOString()` (UTC). The spec requires dates read on hotel local day (WIB, UTC+7), so near midnight the two sides of the same comparison disagree and the AC-1 proof can misclassify.
**Why it matters**: This script is the acceptance evidence for AC-1; a timezone-mixed comparison makes it unreliable exactly at the boundary it claims to prove.
**Suggested fix**: Format both sides in the same zone (compare `yyyy-mm-dd` from one consistent source).

### 🟡 Double pay-now can create two RECORDED rows, `prisma/schema.prisma:153`
**Problem**: `Payment` has no uniqueness on `orderId`, so nothing stops two RECORDED payments for one order; the AC-9 reconcile math (lines minus RECORDED sum) then double-counts. Spec says no partial payments and amount equals the folio share, but neither is guarded.
**Why it matters**: No app code writes payments yet, so this bites in Slice 1, not today — but a unique constraint is a one-line schema guard for a stated invariant.
**Suggested fix**: Add `@unique` on `Payment.orderId` (VOID history stays possible only if re-record semantics are defined) or document that Slice 1 owns the guard.

### 🟡 Cancel-after-verify void path has no coverage, `prisma/data-model.test.ts:116`
**Problem**: The `voided` column exists and the spec requires "cancel after verify keeps folio lines as voided", but no test ever sets `voided: true` and the proof script only covers cancel-before-verify. Likewise `Stay.CANCELLED` blocking ordering is untested. Under `TESTS = configured`, uncovered branching logic is at least Minor.
**Why it matters**: The voided-lines rule is the trickiest folio invariant and currently exists only as a default-false column nobody exercises.
**Suggested fix**: Add a test that verifies an order, cancels it, marks lines voided, and checks the balance excludes them — or record the transition logic as owned by Slice 1 with this test listed.

### 🟡 Missing DATABASE_URL fails late and cryptically, `lib/db.ts:9`
**Problem**: `process.env.DATABASE_URL` is passed straight to `PrismaPg` with no presence check; a missing env var surfaces as an adapter/connection error instead of a clear message.
**Why it matters**: Every later slice imports this client; a one-line guard saves a confusing debug loop for each new checkout.
**Suggested fix**: Throw an explicit error when `DATABASE_URL` is unset.

## Strengths
- The three uniqueness guards that matter most (one ACTIVE stay per room via partial index, one folio per stay, one folio line per order so double-verify fails) are all enforced in SQL and all covered by tests asserting rejection.
- PIN helpers use a fresh random salt per hash, a format-tagged encoding, and fail-closed on malformed input; tests cover cross-stay confusion and repeated wrong attempts.
- `OrderItem.unitPrice` snapshots the price at order time, keeping history correct across later menu edits per the spec's positive consequences.
- The proof script walks the full check-in → order → verify → serve → pay loop including double-verify rejection and balance reconciliation, and the suite (14 tests) passes as claimed — re-verified by the reviewer.
