## Summary

The change moves staff password hashing to bcryptjs inside the BetterAuth config and routes creation, reissue, and seed through the internal adapter seams, retiring direct credential writes. The seam usage mirrors the sign up flow shape and the prove walk passes with live bcrypt rows. Two majors need answers before merge: account creation is no longer atomic, and long passwords silently truncate at the bcrypt 72 byte boundary while the config still allows 128 chars.

## Major
### 🟠 Orphan user when credential link fails, `features/staff/services/staff-service.ts:92`
**Problem**: `createUser` and `linkAccount` are two separate awaits with no transaction, while the retired code wrote both rows in one `prisma.$transaction`. If the link fails after the user lands, the account exists without a credential: sign in never works, the email reads taken so recreate answers 409, and no route deletes staff, leaving manual database repair as the only way out.
**Why it matters**: a database blip in a millisecond window bricks an email address with no recovery path in the app.
**Suggested fix**: wrap the link in try/catch and delete the just created user before rethrowing, restoring the old all or nothing behavior.

### 🟠 Passwords past 72 bytes truncate silently, `lib/auth.ts:36`
**Problem**: bcrypt only reads the first 72 bytes of a secret, but `maxPasswordLength` still allows 128 chars. Two long secrets sharing a 72 byte prefix hash identically, and nothing tells the staffer. Exploitability is low (an attacker needs the first 72 chars), but the weakening is silent.
**Why it matters**: a security boundary that fails silently is worse than one that rejects loudly.
**Suggested fix**: cap `maxPasswordLength` at 72 with the zod message updated to match, or document acceptance of the truncation in spec 0006.

## Minor
### 🟡 Duplicate email race answers 500, `features/staff/services/staff-service.ts:80`
**Problem**: the check then create pattern kept from the old code means two concurrent creates for one email pass the lookup together and the loser throws a raw unique violation instead of the 409 the single flight path returns.
**Why it matters**: admin tooling only, rare, but the error shape lies about what happened.
**Suggested fix**: catch the unique violation in `createStaffAccount` and map it to the same 409.

### 🟡 Successful role change and disable have no test, `features/staff/services/staff-service.test.ts`
**Problem**: `updateStaffAccount` is tested for self guard, bad role, and unknown user, but no test walks a role change or a disable through to the stored row.
**Why it matters**: the happy path of an admin only mutation is exactly what a later refactor could quietly break.
**Suggested fix**: add one test promoting a throwaway kitchen user to front desk and one disabling then re enabling, asserting the stored flags.
